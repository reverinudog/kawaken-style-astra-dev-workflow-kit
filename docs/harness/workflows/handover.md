# ハンドオーバー

「ハンドオーバー」「引き継ぎ」「完了処理」でこの手順を実行する。
導入時にPROJECT.mdへ定めたGit完了の終点を使い、通常の工程切替では再承認を求めない。
今回の依頼とPROJECT.mdから、commit、push、PR、merge、後片付けまでの承認範囲を確定する。
「引き継ぎ」の意味を推測で一般公開やデプロイまで広げない。
承認済みの工程は通常の切替だけで再確認せず終点まで進める。

1. branch、status、基点との差分、所有する変更を確認する。
2. 対応するタスクがあれば結果・証拠・未確認事項を記録し、完了済みだけtasks/done/へ移す。
3. 一覧の登録を更新して文書チェックを行う。未完の作業をdoneにしない。
4. 再発する具体的な教訓があれば[教訓の手順](lessons.md)で既存分類と索引を更新する。作業日誌や通常の成功は増やさない。
5. 自己レビューと必要な独立レビュー、影響に見合う検証を確認する。未変更の成功結果を再利用する。
6. 完了範囲、修正、検証、残る制約、次に行うGit操作を短く示す。
7. 承認されたcommit・push・PR・mergeを実行する。stageするファイルを列挙し、秘密や関係ない差分を入れない。
8. remote上の結果、マージ対象とcommitの作者情報、公開範囲を確認する。必要なら[worktreeの後片付け](worktrees.md)を行う。

## GitHubの作者情報を守る

ローカル設定とGitHub側が生成するcommitの設定は別。privateでも個人メールの混入を許容したことにしない。
本人のGitHubで確認したnoreplyをrepoローカルへ設定し、stage・commit・送信後のauthor/committerも確認する。
**PR作成前にも確認する。** GitHubはPRの比較用に仮マージcommitを生成し、
そこへアカウント側の作者メールを入れる場合がある。ローカルのnoreplyだけでは制御できない。
アカウント側の非公開メール設定と生成commitのidentityが未確認なら、新しい公開候補でPRを作らない。
確認は本人の設定画面と、外部公開しない検証用repoで行う。既存の承認と保護設定が許す場合は、
ローカルでレビュー済みのcommitを、作者情報を保持するfast-forwardで統合できる。
GitHub CLIの対応を`gh pr merge --help`で確認し、merge時は`--author-email`へそのnoreply、
`--match-head-commit`へレビュー済みheadを必ず指定する。未対応・作者指定の拒否時は、その方法でのmergeを止める。
私用メールや指定省略へ自動で切り替えない。既存の承認とbranch保護が許す運用では、
レビュー済みhead・統合先・祖先関係を確認し、作者情報を保持したfast-forwardで統合できる。
新しいcommit生成を伴わない統合でも、remote上のSHAと公開範囲を確認する。PRを使った場合だけPRの統合状態も確認する。
作成されたmerge commitを取得し、メールは値をログへ出さず許可したidentityとの一致を検査する。
PRを使った場合は仮マージのSHAとrefs/pull/*/mergeも監査する。閉じたPRの旧SHAも残り得る。
GitHubのcommitter `noreply@github.com` は正確な一致だけを例外とする。
誤混入時に自動force pushを行わず、影響を説明して具体的な復旧案を用意する。

branch削除は、レビュー済みheadがremote統合先へ到達し、追加の未統合commitがなく、継続作業・共有利用がない場合だけ。
PRを使った場合はそのheadとの一致と統合状態も確認する。PRなしのfast-forwardでは、取得したremoteのSHAと祖先関係を根拠にする。
履歴の強制書換や未統合branchの破棄は通常手順に含めない。
統合先のローカル同期ができない場合は、無理に他作業を切り替えず、その状態を報告する。

通常の実装依頼では検証結果を報告して終了する。Git完了が既に依頼されている場合は最後まで行う。
