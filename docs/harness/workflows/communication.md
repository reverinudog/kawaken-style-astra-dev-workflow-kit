# 説明と相談

利用者に起きること、変更の理由、判断点を平易な日本語で伝える。
専門語や比喩を並べず、操作の順序・条件・結果を直接書く。事実と推測を分ける。

## 説明を開く

説明・提案・相談には、図・表・具体例を含むHTMLを用意して描画した状態で開く。
一画面一テーマの短いスライドを基本にし、詳細仕様はMarkdownへ分ける。
説明だけなら回答欄は不要。短い進捗・単純な結果報告はチャットと既存資料への入口でよい。
工程が変わるたびに別の資料を増やさず、同じ資料の短い更新を優先する。

利用可能ならCodex内蔵ブラウザを使う。ブラウザ表示機能で開き、資料のファイルリンクも添える。
ソース表示や「保存した」という報告だけで提示を終えない。
内蔵ブラウザがない場合は利用可能なプレビューと入口を示し、勝手に外部アプリを前面表示しない。

## HTMLから回答する

修正候補・複数案の採否には[HTML回答の手順](html-feedback.md)を使う。
同じ範囲の現在と提案を1件ずつ比較し、選択・自由記入・途中保存・一覧確認・一括提出を用意する。
既定の選択は置かず、未回答と保留を分ける。コメント必須の選択は内容が入るまで提出させない。
受付・共通クライアントを同梱している。手動添付や「提出した」とチャットへ伝える方法を通常経路にしない。

回答のPC保存、Codexの通知受付、同じタスクでの受領は別々に表示・確認する。
初導入時はテスト提出から実際の同一タスク再開と受領まで確認する。
未接続なら自動受信できると案内せず、入力を保持して接続を修復する。
提出待ちにLLM常駐・heartbeat・定期的なモデル呼出・別タスク作成を使わない。

## 資料・入力・タブを保持する

同じ資料ではURL・保存キー・既存タブを維持する。再起動でもポートを変えない。
内容が変わった時は以前の版の回答を保管し、変更後の内容を自動承認した扱いにしない。
未提出の入力を送信しない。旧タブを閉じる前に途中保存を確認する。
自分が開いた同じ資料の旧版・不要な確認タブだけを閉じ、最新版の閲覧・回答タブを残す。
他の作業やユーザーが使っているタブに一括適用しない。ファイルと回答は削除しない。

ユーザーの回答・途中の追加条件は現在の目的へ反映する。
通常の修正と必要な検証は進めるが、回答をGit統合・一般公開・範囲外操作の承認へ広げない。
