# 利用者向けの更新情報

「リリースノート」「アップデート情報」で使う。文案作成を公開承認にしない。

1. 対象版と、利用者へ実際に届いた前回版のcommitを確認する。タグだけで配布済みと仮定しない。
2. 基点から対象headの差分と完了タスクを読み、実際に含まれる変更だけを拾う。
3. 大きな変更、関連する改善、そのほかの修正の順に、利用者の操作・見える結果で書く。
   差分行数を重要度にしない。同じ体験の重複は統合し、内部関数・branch名・開発だけの変更を並べない。
4. 利用者が指定した表現と製品の正式な用語を保持する。未確認の効能・速度・安全保証は足さない。
5. 草案には基点、対象head、version、確認状態を残す。利用者へ短いHTMLで提示し、修正を反映する。
6. 製品内の短縮案は承認済み全文の意味を保つ。新しい主張を足さない短縮には再承認を挟まない。
7. 公開は[リリース](release.md)の承認範囲で行い、公開後の版と表示を確認する。

空の分類や既に前回配布した項目を数合わせで残さない。基点が変わったら対象差分も見直す。
