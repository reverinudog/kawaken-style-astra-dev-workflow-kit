# 変更に見合う検証

最初に「何が壊れるか」「既存の証拠が使えるか」を考える。
その失敗を直接検出できる、必要十分な最も軽い層で確認する。
すべての編集にunit・E2E・手動・全体試験を重ねない。

| 変更 | 検証の起点 |
| --- | --- |
| 開発文書・手順・スキル | 文書参照チェック、差分確認、正常依頼と反例のシナリオ確認 |
| 小さな表示・文言 | 対象の実画面と状態。振る舞いの変更があればそのテスト |
| 局所ロジック | 変更契約を通すcase/file |
| 共有状態・複数モジュール | 影響する境界と隣接機能を通す対象検証 |
| 保存・権限・課金・AI出力 | 正常と関連する失敗・中断・境界、互換性の確認 |
| テストの登録・検出設定 | 検出・登録チェックと該当テスト |
| 配布・デプロイ | 成果物の構成、隔離環境での起動、対象の主要フロー |

テストコマンドはPROJECT.mdまたは導入先の実装で確認する。推測したコマンドや全suiteを既定にしない。
広げるのは変更境界、未検証の受け入れ条件、指摘、不具合から不足が判明した場合だけ。

## 追加するテストの価値

追加前に、防ぐ不具合と既存テストの不足を明確にする。既存caseの活用・拡張を優先する。
件数の増減を目的にしない。実装の関数名や呼出順を写すだけの検査を増やさない。
一方で、少数にするために保存、権限、失敗、中断、並行処理の重要な穴を残さない。

遅い・不安定な検査は関連範囲で原因修正・統合・同等の検出力を持つ置換を検討する。
時間短縮だけを理由にskip、削除、アサーションの弱体化をしない。
待ち時間を増やす前に、止まっている原因と期待時間を調べる。

## 証拠と終点

実行コマンド、範囲、結果、必要なら所要時間を記録する。
テストが止まった場合は不明として扱い、独立した確認を進める。
親が同じ実操作を何度も別ツールで繰り返す必要はない。

手順やskillでは代表的依頼と適用してはいけない反例を通す。
担当・権限・完了条件のまとまった変更は[独立レビュー](ownership.md)も行う。
開発指示の修正だけで製品の有料AI試験を追加しない。

受け入れ条件に直接の証拠があり、指摘が解消されたら完了する。
未確認の外部環境や美的受け入れは分けて報告し、成功を捏造しない。
