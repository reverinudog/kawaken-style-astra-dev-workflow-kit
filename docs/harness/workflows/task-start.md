# 作業開始

## 調査と境界

1. branch、status、worktree、PROJECT.md、今回の依頼を確認する。
2. 目的、現行の正本、変更する入力・出力・状態・副作用を調べる。[教訓の索引](../LESSONS.md)を症状・境界・ツール名で検索し、関連項目の予防策を今回へ反映する。
3. 「維持する契約」「置き換える仕組み」「対象外」を分ける。名前の類似だけで同じ責任とみなさない。
4. 局所修正で原因を解消できるか、重複・例外・余分な状態を残すかを判断する。必要なら統合・置換・削除を比較する。
5. 構造変更では、呼び出し元、共有状態、初期化・終了、保存・再開、周辺の未編集機能を追う。
6. 完了条件と[検証](verification.md)を決め、調査結果と方針を短く伝える。

仕様書がないだけで停止・新規タスク化しない。直接依頼を起点にできる。
承認済みの範囲内の実装判断で毎回確認を挟まない。相談のみなら設計の説明で止める。

## 実装

編集前にPROJECT.mdの基点から作業branchを作る。既存作業のbranchは再利用する。
別作業でcheckoutが使われている時は[worktree](worktrees.md)で分離する。
今回必要な構造変更は差分量だけで拒まない。製品の意味変更・対象外の整理へ広げない。

実データを書き換える検証は、隔離したデータ領域とサーバー設定で行う。
保存先やサーバーの起動元が不明なら実利用環境として扱い、書込検証をしない。
一括したポート停止や、他作業のプロセス停止を行わない。

## 行き詰まったら

同じ失敗や情報の増えない試行が続いたら、その方法を止める。
観測事実、未確認の仮定、試行で否定できた点を短く整理する。
調べる層や問題の分け方を変え、元の仮説と区別できる最小の確認を選ぶ。

待ち時間の延長や似たコマンドへの置換だけを別アプローチとしない。
再試行は条件の変化や新しい証拠がある時に行う。
既存の成果を保持し、承認範囲や目的を勝手に変えない。切替理由は短く伝える。
