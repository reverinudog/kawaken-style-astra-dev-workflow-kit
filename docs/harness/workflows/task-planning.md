# タスク登録と仕様相談

「後でやる」「タスクにして」は記録の依頼。実装や外部Git操作の承認へ拡張しない。

小さな作業は[タスクテンプレート](../templates/task.md)で目的・範囲・受け入れ条件を記録し、
tasks/直下へ置き、[一覧](../NEXT_TASKS.md)に `- [タスク名](tasks/name.md) — 短い説明` の形式でリンクを一つ追加する。
登録後は文書チェックを実行する。Git完了はPROJECT.mdと今回の依頼に従う。

設計が未確定の大きい作業は、現在の体験、期待する結果、保護条件を調べる。
過去のdone、既存の未完了タスク、関連LESSONS、実装とテストを調べ、重複・競合・前提依存を確認する。
意味の異なる選択肢だけを具体例で示し、判断を受けて仕様へ反映する。
聞き取りのために独立した調査を止めない。相談段階で実装しない。

各タスクは単独で受け入れ・検証・統合できる境界で分ける。
中核データ、未確定API、連動する画面フローをファイル数だけで分割しない。
共通仕様を共有するなら一つの正本へ参照を集める。

仕様には正例・起こしてはいけない例、対象外、失敗・中断・互換性、観測できる受け入れ条件を含める。
既存契約から決められる実装判断は親が埋め、製品の意味が変わる未決定事項だけHTMLの比較回答へ出す。
合意済みの項目を毎回承認し直させない。正式登録前に自己レビューし、未決事項があるものはhold/researchと明記する。
依存が強い工程を細かいタスクへ切り離さず、単独で検証・統合できる場合だけ分割する。
連続実行へ渡すタスクには[離席中の実行](queue.md)の条件を使う。

新しい作業は現在の作業と混ぜない。先送りが大きな手戻りになる場合だけ、具体的な理由と範囲変更を相談する。
