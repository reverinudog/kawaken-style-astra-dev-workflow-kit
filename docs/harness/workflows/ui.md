# UI設計と実画面の確認

画面の目的、最初に見せる情報、主操作、維持する操作・保存・固定文言を決める。
端末・解像度・入力方法はPROJECT.mdと製品の対象から選ぶ。
デスクトップ、モバイル、Webを一律の画面サイズへ押し込めない。

既存部品はfocus、dismiss、入力、状態管理の契約を守るために再利用する。
外観や構図は任された体験に合わせて設計する。カタログにないだけで再承認を求めない。
実測事実、ユーザーの固定条件、原因仮説、未採用モックを区別する。

## 実装前後

- 小修正の比較は現行画面と同じ状態・範囲・視点で作る。対象外の文字や装飾を変えない。
- 大きな再設計では維持すべき動作を固定し、情報の階層や構図から見直せる。
- 実データ相当の通常・空・長文・最大件数と、変更に関係する読み込み・失敗・戻るを確認する。
- 見栄えのために存在しない機能や偽の成功状態を足さない。注入したfixtureは記録する。

## 全画面で確認すること

主操作が分かること、文字が読めること、重なり・欠け・操作不能がないことを実画面で確認する。
重要情報を縮小や省略記号で隠さず、折返しや適切な内部スクロールを検討する。
変更した操作を実際に試し、処理中・成功・失敗・再試行・戻るの結果を確認する。
focus、keyboard操作、スクロール、重なる要素の実際のクリック対象も変更に応じて確かめる。
動きがある場合は入力の妨害や時間関係を動作で確認し、静止画だけで終えない。

見出し、本文、HUD、footer、ラベル、数値、選択状態、アイコンを離れた位置まで見渡し、
同じ意味の重複や矛盾を探す。必要な確認、アクセシブル名、単独通知の文脈は残す。
文言は対象・条件・操作・結果を直接表し、実処理と一致させる。
創作本文やキャラクターの台詞には、操作案内用の短文化を一律適用しない。

証跡はscreenshots/以下へ保存し、個人データを使用しない。
自分が作った不要な確認タブは閉じ、ユーザーの作業タブや未保存入力を保持する。
主観的な見た目の完成は実画面でユーザーへ示し、AI採点を美的承認の代用にしない。
